# Cloudflare server agent brief

## Objective

Maintain the Cloudflare service under `server/`: Worker API, D1 migrations, private R2 recording storage, fixtures, and an Access-protected admin page. Start with [server/README.md](../server/README.md) for runnable self-hosting and operational instructions.

## Ownership

Own `server/**` and this role brief; do not edit `android/**` or the frozen [API contract](../docs/API_CONTRACT.md). Claim an eligible backend task in `tasks.json` and respect its paths and dependencies. Only the designated integration owner updates the task manifest or shared integration files during parallel work.

The frozen contract defines the original v1 boundary. The approved additive sections below define employee/device management, call history, recovery, independent deletion, and Samsung association. Preserve both; propose further interface changes here for reconciliation rather than silently changing the frozen contract. Source and ordered migrations describe the implemented behavior; the older [Cloudflare plan](../docs/CLOUDFLARE_PLAN.md) is design background.

## Implementation invariants

- Keep one shallow TypeScript Worker deployment with explicit D1 `DB` and private R2 `RECORDINGS` bindings. Local and remote setup, secrets, Access, retention and rollback belong in the server README.
- `createIdentityRepository` owns employees, hashed invitations, atomic registration, device authentication/revocation, assignment history and diagnostic heartbeats. Store no plaintext invitation or bearer credentials. `TOKEN_HASH_SECRET` requires at least 32 bytes and must stay stable.
- `createCallRepository` owns idempotent `(deviceId, fingerprint)` creation, immutable server-generated object keys, upload states and filtered keyset pagination. Repository models are not wire responses.
- Prepare validates metadata, audio content type and byte limits. Signed Worker upload capabilities scope a streamed PUT to one server-generated R2 key. Never return account-level storage credentials or a public bucket URL.
- Complete verifies R2 object existence and size, then atomically checks active ownership before marking complete. Repeated prepare/complete preserves identity. A device may complete a pending upload after reassignment while the device and relevant employees remain active.
- Playback uses expiring capabilities. Recording deletion removes R2 audio, retains a tombstone, is retryable/idempotent and immediately invalidates prior playback access. Independent history deletion has the additional semantics below.
- Normalize timestamps to millisecond UTC. Recording order/date filters use `recordedAt`, falling back to `createdAt`, with opaque call ID as pagination tie-breaker. Preserve source timestamps and historical attribution.
- Remote admin routes validate Access JWT signature, issuer, audience, expiry, subject and email. Local sign-in is development-loopback-only, secret-backed, expiring and HttpOnly; cookie mutations require same-origin requests. Only the local login page uses `Referrer-Policy: same-origin` so native form POSTs supply a valid origin; other routes retain `no-referrer`.
- Access key retrieval uses `redirect: "manual"` and rejects non-2xx responses. Do not follow JWKS redirects or weaken JWT validation to work around runtime behavior.
- Keep D1 ownership/revocation checks transactional. Wrangler migrations require compatible SQL; flat `SELECT RAISE(...) WHERE ...` guards avoid the nested trigger `CASE ... END` parsing problem.
- Keep admin calls compact and newest-first, with server-side filters, opaque cursor pagination, inline audio/download, explicit deletion confirmations, employee management, reassignment and one-use enrollment/recovery. Render names/numbers literally, show revoked items only when requested and keep unknown/unlinked states visible.
- Shared fixtures under `server/fixtures/` cover registration, matched and unmatched preparation, completed calls, pagination and standard errors. Use synthetic audio and identities only.

## Verification boundaries

Follow the repository's local-check policy and the integration owner's coordination before running checks. Relevant contracts include schema/error validation, atomic single-use registration/recovery, credential hashing and revocation, cross-device isolation, historical attribution, prepare/complete retries, content/size limits, filtered pagination, capability expiry and independent deletion. Exercise the actual Worker/D1/R2 lifecycle and admin UI when validating integrated changes.

Hardware-dependent behavior needs its own evidence: physical Samsung folder access, installer-granted call-log permission, dual-SIM reporting, older Android compatibility, long-running scheduling and interrupted-upload recovery are not established by backend tests. No deployment or hardware verification status is implied by this public brief.

## Approved employee and enrollment extension

Stable server enrollment is independent of SIM changes. The existing `deviceId` is the enrollment ID; it is public, immutable, and never an authentication secret. Existing per-device bearer credentials remain authoritative. Phone numbers are unverified, read-only device-reported metadata, not credentials. No shared APK secret or plaintext invitation storage is introduced. These approved additive interfaces supplement the frozen `docs/API_CONTRACT.md`.

- `GET /v1/admin/employees?cursor=&limit=50`: `{requestId, items: Employee[], nextCursor}`. `Employee` retains `id`, `name`, optional legacy `phoneNumber`, `active`, `createdAt`. Limit 1–100, stable newest-first keyset pagination.
- Existing `POST /v1/admin/employees` also returns the complete public `Employee` in `{requestId, employee}` with 201, adding `active` and `createdAt` so immediate management actions do not need a second lookup.
- `PATCH /v1/admin/employees/{employeeId}` with `{name}`: `{requestId, employee}`. The UI edits names, not SIM-reported numbers. Existing legacy employee phone values remain distinct from device reports.
- `GET /v1/admin/devices?employeeId=&cursor=&limit=50`: `{requestId, items: ManagedDevice[], nextCursor}`. `ManagedDevice` exposes `id`, `employeeId`, `employee: {id,name}`, device model/version fields, `phoneNumbers: string[]`, optional `phoneNumbersReportedAt`, `createdAt`, `assignedAt`, optional `lastSeenAt`, `pendingUploads`, `revokedAt`. Never expose credential hashes.
- `PATCH /v1/admin/devices/{deviceId}` with `{employeeId}`: `{requestId, device: ManagedDevice}`. Atomically reassign a non-revoked device to an active employee, recording assignment history. Enrollment ID and credential do not change.
- `POST /v1/admin/devices/{deviceId}/revoke`: `{requestId, device: ManagedDevice}`; idempotent. Revoked devices cannot report status or upload.
- `GET /v1/admin/employees/{employeeId}/invitations?cursor=&limit=50`: `{requestId, items: InvitationSummary[], nextCursor}`. Entries contain `id`, `employeeId`, `createdAt`, `expiresAt`, optional `redeemedAt`/`revokedAt`, and `status: active|redeemed|expired|revoked`. No recoverable code text. Existing creation returns its fresh secret once and additionally returns `invitationId`.
- `POST /v1/admin/employees/{employeeId}/invitations/{invitationId}/revoke`: `{requestId, invitation: InvitationSummary}`. Prevent subsequent redemption; never revoke a device already registered from that code. Replacement means revoking an unused invitation and issuing a fresh random one, not choosing weak reusable codes.
- Registration's existing `device` object accepts optional `phoneNumbers: string[]` (up to eight nonempty, trimmed strings, each at most 64 characters). Heartbeat accepts optional `deviceId` and `phoneNumbers`; a supplied enrollment ID must equal the bearer-authenticated device or return 401. New clients send both on every heartbeat. Omission retains earlier phone metadata; an empty array explicitly clears it.
- Heartbeat response adds `deviceId` and `employee: {id,name}` to existing `requestId`/`serverTime`, so an enrolled client refreshes its assignment without employee configuration. Unknown or unreadable SIM numbers are reported as an empty list, never invented.
- Historical `calls.employee_id` is immutable. For newly prepared offline recordings with `recordedAt`, resolve the employee from assignment history; preserve the initial assignment for pre-enrollment recordings, matching existing behavior. After a handover, a newly prepared recording without a timestamp is ambiguous and must return 409 rather than guess. Existing fingerprint replays retain original ownership. A pending recording can finish after reassignment while the device and relevant employees remain active.

### Approved full call-history extension — 2026-09-25

The user requested full phone call history, including missed/unrecorded calls, alongside recording uploads. Phones receive manually opened APKs. Android must disclose collection and request the real permission; installer-restricted or denied call-log access is a visible unsupported state, never bypassed. The simplified-setup extension below defines current consent controls and conservative audio association.

- `POST /v1/device/call-logs/batch`: authenticated JSON `{deviceId, entries}` with 1–50 entries. The supplied enrollment ID must match the bearer-authenticated device. Each entry has `fingerprint` (64 lowercase hexadecimal), `startedAt` (UTC RFC 3339), `durationSeconds` (integer, 0–604800), `callType`, and optional `remoteNumber` (1–80 characters). Call types are `incoming`, `outgoing`, `missed`, `rejected`, `blocked`, `voicemail`, `answered_externally`, `unknown`.
- The enriched batch byte bound is defined in the simplified-setup extension below. Other JSON mutation endpoints retain the 16 KiB limit.
- Success is `200 {requestId, accepted: [{fingerprint, id}]}` for every input entry. Validate the whole batch before writing. Upserts are scoped to `(deviceId, fingerprint)`; replays may refresh duration/type/number but never change the original start time or employee. Resolve initial attribution from device assignment history at `startedAt`, including pre-enrollment history under the initial assignment. Device revocation and active employee checks remain authoritative.
- `GET /v1/admin/call-logs?employeeId=&callType=&number=&from=&to=&cursor=&limit=50` is guarded and returns `{requestId, items, nextCursor}`. The current unified item shape and association rules are defined below. Limit is 1–100 and number matching is literal, not SQL wildcards.
- Android history fingerprints derive from enrollment ID, provider row ID and call-start timestamp, not mutable duration. A durable outbox checkpoints before HTTP and accepts a row only after its fingerprint is acknowledged. Missing/restricted caller numbers are omitted. No contacts permission or dialer-role substitution is introduced.
- Recording uploads retain the existing prepare/streamed PUT/complete API. Selected-folder access uses persisted Storage Access Framework read grants, with no broad filesystem permission. Completed/stable files are tracked in a local ledger; retries retain their fingerprint/call ID and attempt completion before retransmitting successful PUTs. Unknown recording timestamps remain omitted rather than inferred from file modification times.

### Approved simplified setup and unified calls — 2026-09-26

The user requested event-driven synchronization, a simple permission checklist with one grant flow, advanced diagnostics separately, no in-app pause or per-feature switches, compact unified call/recording administration, call-specific line identity, and visible invitation provenance. Android permission revocation/uninstall controls remain intact; the named status notification and launcher remain visible. The user selected administrator-issued one-use recovery for the existing enrollment after reinstall, not reusable invitation codes or hidden credential persistence.

- History batch entries additionally accept optional `callerName` (1–256 characters), `localNumber` (1–80), `simLabel` (1–120), and `phoneAccountId` (1–256). The bounded 50-entry endpoint allows 256 KiB. Names come from Android's cached call-log name without bulk contacts access. Line data comes from the specific call's phone-account handle, never from a default SIM or list ordering. Unknown fields are omitted. Retain the first nonempty historical line/account snapshot rather than rewriting old calls when the SIM changes.
- `GET /v1/admin/call-logs` becomes a unified feed, retaining existing filters and opaque pagination, adding optional `hasRecording=true` for completed playable audio. A history item retains its existing fields and adds `kind: "call"`, the optional enrichment fields, and `recordings: AdminCall[]` using the existing public recording-list representation.
- An unlinked recording is an item with `kind: "recording"`, its recording `id`, `deviceId`, `employee`, `createdAt`, optional `startedAt` only when source `recordedAt` exists, and `recordings: [AdminCall]`. It has no invented call type or caller/line metadata. Sort it by source time when known, otherwise creation time; label that fallback as upload time. A call-type filter excludes unlinked recordings. The recording checkbox includes only rows with complete audio.
- Association is unique within the same device and historical employee, independently of filters/pagination. The original exact-second/source-start rule is superseded for proven Samsung filenames by the [corroborated association rules](#samsung-recording-association--2026-09-27). Missing or competing evidence remains visibly unlinked; file modification/upload time and merely the newest call never establish a match. Recompute as either stream arrives; multiple recordings may belong to one unambiguous call.
- `GET /v1/admin/devices` and `GET /v1/admin/employees/{employeeId}/invitations` add `includeRevoked=true`, default false. Apply exclusion before pagination. Managed devices and register/heartbeat responses add optional `invitationId` (original setup) and `lastInvitationId` (latest setup/recovery). Invitation summaries add `purpose: "enrollment" | "recovery"`, optional `deviceId` for redeemed enrollment, and optional `recoveryDeviceId` for a recovery target. Never expose codes/hashes in lists. Legacy provenance may be backfilled only when original redemption/creation timestamps and employee form a unique one-to-one match; otherwise report unknown.
- `POST /v1/admin/devices/{deviceId}/recovery-invitations` uses the existing invitation expiry rules and response shape `{requestId, invitationCode, invitationId, expiresAt}`. Require an active employee and non-revoked device. Atomically supersede outstanding recovery codes for the target. Issuance does not disable the currently working installation.
- Redeem recovery through the existing `/v1/device/register` endpoint. Atomically consume the one-use code and rotate the target's bearer hash, retaining enrollment ID, employee attribution, assignment history, recording identities and original invitation ID. Update device metadata and `lastInvitationId`; invalidate the old bearer credential. Reject replay, expiry, revocation, inactive employee and reassigned-target conflicts without partial mutation. Android must grant permissions/folder access again after uninstall; public IDs alone never authenticate.

### Approved Linekeep identity and independent deletion — 2026-09-27

- **Linekeep** is the public product name. Existing installations must retain Android application ID `com.microorganics.calltracker`, persisted keys, backend URL/resources, authentication identities and signing key to remain upgrade-compatible. Generic Linekeep resource names in public setup templates are for new self-hosted deployments, not a migration of existing enrollments.
- Add administrator-only `DELETE /v1/admin/call-logs/{callLogId}`, returning `{requestId, callLogId, status: "deleted"}` idempotently. Remove the history entry from the unified feed and retain a server tombstone so ordinary device replay acknowledges but does not restore it.
- Deletion actions are independent and explicit: deleting a call log keeps its recordings, now visibly unlinked; deleting a recording removes its stored audio but keeps the call log. Neither action deletes anything from the phone. Reuse existing recording deletion and its authorization/capability protections. Hide deleted recordings from the unified feed, retaining the existing legacy tombstone API semantics.
- Association remains conservative after deletion: a deleted history candidate must not make previously ambiguous audio suddenly attach to another call. Preserve that ambiguity evidence while excluding deleted candidates from live association.
- History deletion retains internal matching/deduplication metadata; the confirmation must disclose that retention. This endpoint is not a full privacy-erasure workflow.

### Samsung recording association — 2026-09-27

- Migration `0007_recording_association.sql` changes association only. HTTP responses, Android metadata/storage identities and the frozen API contract remain unchanged. Samsung media may contain a recording-end timestamp while the filename contains its start and Android history has an earlier call-start timestamp; matching must corroborate those sources rather than rewrite them.
- Recognize only the observed `Call <name-or-number>_YYMMDD_HHMMSS.m4a` format. Require an exact cached-name match (ASCII case-insensitive) or full telephone digits after removing presentation punctuation; do not guess country codes or match number suffixes.
- Require positive durations within two seconds. Either the embedded timestamp or that timestamp minus recording duration must be 0–30 seconds after the Android call start, evaluated to whole seconds. Corroborate that inferred recording start against the valid filename calendar timestamp: their difference must be a plausible UTC offset (-12h through +14h, on a 15-minute boundary), within two seconds of rounding. Do not assume the server/device timezone or rewrite source timestamps.
- Other filename conventions retain the exact-second, equal-duration rule. All candidates require the same device and historical employee, incoming/outgoing history and no conflicting known number or direction. Count the full candidate set, including deleted history; attach only one unique live candidate. Name, filename, number, direction and duration updates recompute transactionally in either stream order.
- The migration replaces duplicated trigger predicates with one candidate view and duration-oriented indexes, then backfills existing recordings. It changes associations only, not history, audio, raw timestamps, names, upload states or employee attribution.
- Keep duration-oriented candidate indexes so matching a recording does not require a full-history scan. Regression coverage must retain both stream orders, numeric formatting, rounding boundaries, identity/direction conflicts, calendar/offset checks, missing metadata, caller-name changes, full-set ambiguity after deletion, employee/device isolation and migration preservation of raw recording fields.

### Daily call-summary email — 2026-09-28

- The existing Worker also handles scheduled events. Cloudflare Cron `30 12 * * *` runs at 6 PM IST. No HTTP contract, authentication route, Android behavior or database migration changes.
- `server/src/reporting/call-summary.ts` aggregates undeleted canonical `call_logs`, not recordings or paginated unified-feed rows. Use immutable log employee attribution rather than the device's current owner. Global unique-number counts must not sum per-employee counts.
- The approved window is the scheduled event's IST date, midnight inclusive to 6 PM exclusive. Emails explicitly describe a today-so-far snapshot: post-cutoff calls and uploads arriving after generation are not carried into tomorrow's report. Preserve UTC/IST boundary behavior and the fixed cutoff on delayed invocations.
- HTML and plain text contain overall/per-employee counts, duration and all call types, but no call-number fields, audio or media URLs. Escape employee names in HTML. Connected means positive logged duration, not verified audio or a separate phone-system disposition.
- Mailgun uses `EMAIL_IDS`, `MAILGUN_API_KEY` and `MAILGUN_DOMAIN` secrets, with optional `MAILGUN_FROM_EMAIL` and `MAILGUN_REGION` (`us` default or `eu`). Recipient configuration accepts comma-separated addresses or a JSON array; recipients share the To header. Activation requires explicit `CALL_SUMMARY_ENABLED=true` per environment.
- Keep public templates disabled and free of real recipients/provider identities. Never export GitHub secret values through workflow logs. Provider bodies and configuration errors must not leak secret values; use native Worker-compatible `redirect: "manual"` and reject non-200 responses. A successful send is provider acceptance, not confirmed delivery or an exactly-once guarantee.
- Focused coverage: `node --test src/reporting/call-summary.test.mjs`. Native workerd verification is important: Node fetch accepts redirect modes that Workers reject.

### Customers, WhatsApp chats and employee assignment — 2026-10-06 (approved by project owner)

Adds customers, employee assignment and stored WhatsApp conversations. Existing endpoints, migrations 0001–0007 and `docs/API_CONTRACT.md` are unchanged. All new JSON responses carry `requestId`; errors use the existing `{requestId, error:{code,message}}` shape (`INVALID_REQUEST` 400, `NOT_FOUND` 404, `CUSTOMER_PHONE_EXISTS` 409, `WHATSAPP_NOT_CONFIGURED` 503). Pagination follows the existing opaque-cursor, `limit` 1–100 (default 50), newest-first convention. Query parsing rejects duplicates/unknown keys like the call-history routes.

**Data model (migration `0008_customers.sql`, additive only).**
- `customers`: `id` (`cus_<uuid>`), `name` (required, 1–200), `phone` (required, normalized `+<digits>`), `phone_key` (last 10 digits), `email`, `notes` (≤4000), `source` (≤120), `district`, `state` (≤120), `country` (default `India`), `created_at`, `updated_at`, `archived_at`. Only `name` and `phone` are required. `phone_key` is unique among non-archived customers; a duplicate returns `409 CUSTOMER_PHONE_EXISTS`.
- `customer_employees`: `(customer_id, employee_id)` unique with `assigned_at`. A customer may have several handling employees. Assignment is a current set; removal deletes the row. Only active employees may be assigned.
- `whatsapp_messages`: `id` (`wam_<uuid>`), `customer_id`, `external_id` (provider message id, unique when present), `direction` (`in`|`out`), `message_type` (text, image, document, template…), `body`, `media_url`, `template_name`, `status` (`queued`|`sent`|`delivered`|`read`|`failed`), `from_number`, `to_number`, `sent_at` (UTC ms, order key), `delivered_at`, `read_at`, `sent_by_employee_id` (null for imports/inbound), `source` (`import`|`app`|`provider`), `created_at`. Index `(customer_id, sent_at DESC, id DESC)`.
- **Phone normalization** (one shared function, used for input, storage and matching): strip non-digits; 10 digits → `+91<digits>`; 11 digits starting `0` → `+91<last 10>`; otherwise `+<digits>` and require 8–15 digits, else `400 INVALID_REQUEST`. **Call matching** compares `phone_key` with the last 10 digits of `call_logs.remote_number` (digits only; numbers shorter than 10 digits never match). Deleted call logs (`deleted_at`) are excluded. Add whatever index/column keeps this from scanning all call history.

**Shapes.**
- `Customer`: `{id, name, phone, email?, notes?, source?, district?, state?, country, employees:[{id,name}], messageCount, lastMessageAt?, lastCallAt?, createdAt, updatedAt}` (absent optional fields are omitted, never `""`).
- `WhatsAppMessage`: `{id, customerId, direction, messageType, body?, mediaUrl?, templateName?, status, fromNumber?, toNumber?, sentAt, deliveredAt?, readAt?, sentBy?:{id,name}}`.
- `ChatSummary`: `{customer:{id,name,phone}, employees:[{id,name}], lastMessage:{direction, messageType, text (≤200 chars, may be empty for media), sentAt}, messageCount}`; sorted by `lastMessage.sentAt` desc; customers without messages are excluded.
- Customer calls reuse the existing unified-feed `kind:"call"` item (employee, callType, startedAt, durationSeconds, `recordings: AdminCall[]`) so audio playback/download URLs and deletion rules are unchanged. Calls are the matched call-log rows from **any** employee/device, so an admin sees who called, when, and the recordings.

**Admin endpoints** (same Access/local-admin guard as other `/v1/admin` routes):
- `GET /v1/admin/customers?q=&employeeId=&unassigned=true&source=&state=&cursor=&limit=` → `{items: Customer[], nextCursor}`. `q` is a literal case-insensitive match on name, phone digits, email (no SQL wildcards). Archived excluded. Order: newest `updatedAt` first.
- `POST /v1/admin/customers` body `{name, phone, email?, notes?, source?, district?, state?, country?, employeeIds?}` → `201 {customer}`.
- `GET /v1/admin/customers/{id}` → `{customer}`.
- `PATCH /v1/admin/customers/{id}` any subset of the writable fields; optional fields accept `null` to clear; changing `phone` re-checks uniqueness → `{customer}`.
- `PUT /v1/admin/customers/{id}/employees` body `{employeeIds: string[]}` (0–50) replaces the set → `{customer}`.
- `DELETE /v1/admin/customers/{id}` → `{customerId, status:"archived"}` (idempotent; keeps messages).
- `GET /v1/admin/customers/{id}/messages?cursor=&limit=` → `{items: WhatsAppMessage[], nextCursor}` newest first.
- `GET /v1/admin/customers/{id}/calls?cursor=&limit=` → `{items, nextCursor}` (unified call items, newest first).
- `GET /v1/admin/whatsapp/chats?q=&employeeId=&cursor=&limit=` → `{items: ChatSummary[], nextCursor}`.

**Device endpoints** (existing device bearer credential; the enrolled device's *current employee* determines access). Customers not assigned to that employee return `404 NOT_FOUND`, never `403`, and are absent from lists. Revoked devices and inactive employees get the existing `401`.
- `GET /v1/device/customers?q=&cursor=&limit=` → `{items: Customer[], nextCursor}` (assigned, non-archived; each `employees` list contains all handlers).
- `GET /v1/device/customers/{id}` → `{customer}`.
- `GET /v1/device/customers/{id}/messages?cursor=&limit=` → `{items, nextCursor}`.
- `GET /v1/device/whatsapp/chats?q=&cursor=&limit=` → `{items: ChatSummary[], nextCursor}`.
- `GET /v1/device/whatsapp/status` → `{canSend:boolean}`. `canSend` is `false` until a WhatsApp transport is configured; there is none yet.
- `POST /v1/device/customers/{id}/messages` body `{clientMessageId (uuid), text (1–4096)}`. Validate the body and assignment, then return `503 WHATSAPP_NOT_CONFIGURED`; store nothing and send nothing. When a transport is chosen, the same request will queue/send idempotently by `clientMessageId` and return `202 {message: WhatsAppMessage}`.

**Authorization decision.** The device bearer token already identifies the enrolled device and its current employee, so no new credential is needed. Employees see only assigned customers. The app never sees other employees' private data beyond the names of co-handlers. Admin access remains Cloudflare Access only. A phone number alone never grants access.

**Out of scope until a transport exists:** actually sending or receiving WhatsApp messages, delivery receipts, media download, templates and the 24-hour messaging window. Historical chats are loaded by an operator import, not by an endpoint.

### Call analytics — 2026-10-18 (approved by project owner)

Read-only aggregation over undeleted `call_logs` (never recordings or paging the unified feed). Admin-only; no migration; no device endpoint.

`GET /v1/admin/analytics/calls?from=YYYY-MM-DD&to=YYYY-MM-DD&employeeIds=a,b&callTypes=incoming,outgoing`
- Days are **Asia/Kolkata (IST, UTC+05:30)**, both ends inclusive: window `[from 00:00 IST, to+1 00:00 IST)` on `started_at`. Defaults: `to` = today (IST), `from` = `to` − 6 days. Max 366 days; `from > to`, bad dates, unknown ids/types or duplicate/unknown query keys → `400 INVALID_REQUEST`. `employeeIds`/`callTypes` are comma lists (≤50 / subset of the 8 call types); absent = all. Employee filter applies to the historical `call_logs.employee_id`.
- Response `{requestId, range, totals, previous, employees, byType, byDay, byHourWeekday, durationBuckets}`:
  - `range`: `{from, to, days, timezone:"Asia/Kolkata", previousFrom, previousTo}`; previous = the immediately preceding window of equal length.
  - `Metrics` (used by `totals`, `previous` and every `employees[]` item, which also has `id`,`name`): `{total, connected, notConnected, uniqueContacts, talkSeconds, avgConnectedSeconds, incoming, incomingSeconds, outgoing, outgoingSeconds, missed, rejected, other, withRecording}`. **connected** = `duration_seconds > 0` (any type; same as the daily email); `talkSeconds` = sum of duration; `uniqueContacts` = distinct non-empty `remote_number` within that scope; `other` = blocked + voicemail + answered_externally + unknown; `withRecording` = calls having a completed, non-deleted recording linked via `calls.call_log_id`; `avgConnectedSeconds` = round(talkSeconds / connected) or 0.
  - `employees`: only employees with ≥1 call in scope, sorted `total` desc then name.
  - `byType`: all 8 types in fixed order `incoming, outgoing, missed, rejected, blocked, voicemail, answered_externally, unknown`, each `{type, count, seconds}` (zeros included).
  - `byDay`: one item per IST day in range (zeros included) `{date, total, connected, talkSeconds, types:{<type>:{count,seconds}}}` with all 8 type keys.
  - `byHourWeekday`: 168 cells `{weekday (0=Sunday), hour (0–23, IST), count}` (zeros included).
  - `durationBuckets` (connected calls only, in order): `{key, label, count}` for `1-29s`, `30-59s`, `1-3m`, `3-10m`, `10m+`.
- Counts and seconds are integers; no phone numbers, names of contacts or recording URLs appear anywhere in the response. Employee names are literal text.

### Approved employee app extension — 2026-11-06 (approved by project owner)

Employees get their own call analytics, call log, and can add and edit their own customers. Everything is derived from the device bearer's employee; no endpoint accepts an employee id, and every query binds it in SQL (nothing is filtered after fetching). Migration `0018_customer_created_by.sql` adds `customers.created_by_employee_id` (nullable, additive).

Chat attachments, outbound media and templates with an image/video/document header. Migration `0019_whatsapp_outbound_media.sql` (additive): `whatsapp_attachments` and an index on `whatsapp_messages.media_key`.

The stored message has `messageType` `image|video|document` (media) or `template` (template header file) and a `media` object `{kind, mimeType, fileName, size, url}` served by the existing message-media endpoints (`/v1/admin/...` or `/v1/device/...` by caller).
- Errors: `409 window_closed` for text/media when the customer's last inbound message is older than 24 h (replaces `TEMPLATE_REQUIRED`; also when Meta answers its re-engagement error 131047); templates are always allowed. `400 template_header_image_required` when a media-header template has neither an override nor a configured default. `400 unsupported_media_type` when an image is WebP (WhatsApp takes JPEG/PNG only) or an override's kind does not match the header. `404 attachment_not_found`.

Header variables and unsupported buttons are still refused. `GET /v1/device/whatsapp/quick-messages` already existed. `GET /v1/{admin,device}/whatsapp/templates/{name}/header-image` serves the configured default.
- Default header per template (admin only, stored in `app_settings` as `whatsapp.templateImage.<name>` → attachment id): `GET /v1/admin/whatsapp/template-images` → `{items:[{templateName, attachmentId, kind, mimeType, fileName, size}]}`; `PUT /v1/admin/whatsapp/template-images/{name}` `{attachmentId}` (checks the file against the template's header format in Meta; `400 header_mismatch`); `DELETE …/{name}`.

### Manager level — 2026-11-13 (owner request)

Proposed contract change, recorded here because the original API contract is frozen. Migration `0023_manager_role.sql` (additive): `employees.role` (`employee|manager`, default `employee`), `employees.manager_id` (nullable, references a manager), `employees.notify_team_messages` (0/1, default 0), an index, and three triggers that make the hierarchy rules hold for any writer (`invalid_manager`, `manager_has_team`).

**Model.** A manager sees, and can do everything an employee can do for, themselves and their team. A *team* is the active employees whose `manager_id` is the manager (at most 50). The *scope* of a manager is `{manager} ∪ team`; an employee's scope is just themselves. A customer is in scope when **any** of its handlers is in scope. The scope is resolved once per request (`server/src/data/scope.ts`, `modules/identity/scope.ts`) and every employee-facing query binds `employee_id IN (...)` in SQL. Managers get no admin power (no employees tab, settings, delete, bulk add, auto-replies, activity log). `lastActive` is unchanged and `team_view` is not logged.

**Hierarchy rules** (admin API, also guarded by triggers): one level only (a manager has `manager_id` NULL; an employee can report only to an *active manager*; a manager cannot report to anyone — `400 manager_cannot_report`; bad target — `400 invalid_manager`; full team — `409 team_full`). Promoting an employee clears their `managerId`. Demoting a manager who still has active reports is `409 manager_has_team` unless the same PATCH carries `moveTeamTo` (another active manager id, or `null` to leave the reports without a manager); inactive reports are always detached. `setEmployeeActive(id, false)` on a manager detaches their reports (there is still no admin route that deactivates an employee, so nothing is logged for it).

**Admin API.** `POST /v1/admin/employees` and `PATCH /v1/admin/employees/{id}` accept `role`, `managerId` (string|null), `notifyTeamMessages` (bool); PATCH also `moveTeamTo` (see above, valid only when demoting). Employee objects carry `role`, `managerId`, `managerName`, `teamSize` (active reports), `notifyTeamMessages`. Activity (category `admin`): `role_changed {from,to}`, `manager_changed {from,to}` (names; `none`), `team_detached {count, employees, reason}`; `employee_updated` may list `notifyTeamMessages`. Category `customer`: `customers_handed_over` (actor = the manager, target = the customer, details `added`/`removed` counts and `to`/`from` employee names).

**Employee profile.** `GET /v1/device/profile`, `GET /v1/web/profile`: `employee` gains `role`, `managerId` (string|null), `team:[{id,name,phoneNumber|null}]` (active reports; `[]` for non-managers). The web sign-in/verify/`session` bodies' `employee` carries the same three fields.

**Scoped reads** (same paths under `/v1/device/*` and `/v1/web/*`; a non-manager that sends a manager-only parameter gets `400 {error:{code:"not_a_manager"}}`; an employee id outside the scope is `400 employee_out_of_scope`; anything outside the scope by id is `404`).
- Filter `employeeId=<id|me|team>` (managers only; `me` = the manager alone, `team` = active reports only, an id must be in scope) on `GET /customers`, `GET /customers/{id}`, `GET /customers/{id}/messages`, web `GET /customers/{id}/calls`, `GET /whatsapp/chats`, `GET /whatsapp/unread` and `GET /call-history`. A customer is matched when any handler is in the selected set. Without it, the whole scope.
- Customer and chat items keep `employees:[{id,name}]` (all handlers) and, for managers only, add `scope:'own'|'team'` (`own` = the manager is a handler). On chat items `employees` and `scope` are on the chat item itself.
- WhatsApp: chats, unread totals, mark-read, status/version, send text/template/media, message media and templates follow the scope. Unread counts and read markers stay per viewer (the manager's own). A manager sending to a team customer is recorded as the sender (`sentBy`). Attachments stay owned by the uploading device/session.
- `GET analytics`: managers may pass `employeeIds=a,b` (subset of scope; default = manager + all active reports combined) and `groupBy=employee`. Response shape unchanged, except `employees` lists **everyone included** as `{id,name,...metrics}` (zero-filled for people with no calls; the plain `{id,name}` fields are a subset) and, with `groupBy=employee`, `byEmployee:[{id,name,...metrics}]` (the people with calls, as the admin report's `employees`). Non-managers: unchanged; `employeeIds`/`groupBy` → `400 not_a_manager`.
- `GET call-history`: `employeeId=<id|me|team>` as above; items already carry `employee:{id,name}`; `customer:{id,name}` is named when the number belongs to a customer in the viewer's scope. Recording playback for scope members' calls: `GET /v1/web/call-history/{callId}/recording` (+ `/audio`) and, new, `GET /v1/device/call-history/{callId}/recording` (+ `/audio`, bearer + the signed URL) — the device route exists only for managers (`404` for everybody else); each playback is logged (`call/recording_played`, actor = the viewer).
- `GET customers/lookup`: for managers `mine` means "in my scope" and a hit also returns `handlers:[{id,name}]` (all handlers). Employees: unchanged, no `handlers`.

**Writes.**
- `POST /customers` accepts optional `employeeId` (a manager may create for themselves or an active report; default self; `createdBy` = the manager; the report gets the existing "New customer assigned" push; non-manager → `400 not_a_manager`, out of scope → `400 employee_out_of_scope`). A number held by a customer in the caller's scope is reported with its `customerId` (`409 customer_exists`), otherwise a bare conflict.
- `PUT /v1/{device,web}/customers/{id}/handlers` `{employeeIds:string[]}` (strict; managers only): the handler set **inside the manager's scope** becomes exactly `employeeIds` (every id must be in scope, `400 employee_out_of_scope`); handlers outside the scope are preserved. Newly assigned employees get the push (never the manager); returns `{customer}` (with `scope`). An empty array is fine while an outside handler remains; a result with zero handlers in total is `409 handler_required` (deviation from the draft: a manager cannot unassign a customer completely). A customer not in scope is `404`. Logged once as `customers_handed_over`.
- `PATCH /customers/{id}` (name, notes; phone → `400 phone_not_editable`) applies to the scope; response carries `scope` for managers.

**Push.** `employees.notify_team_messages` (admin-editable, off by default): when on, the manager is also pushed new inbound messages of customers handled by their active reports (same push as a handler gets). No client UI is needed.

**Deviations / notes.** No admin route deactivates an employee, so the deactivation detach is repository-level only. `moveTeamTo` is an added convenience for the "move team" flow. Scope is limited to 50 reports per manager so every predicate fits D1's 100-bind limit. Verified with `src/modules/identity/manager.test.mjs` (scope matrix, handover, hierarchy, push, DB guards, admin script) and `src/data/manager-migration.test.mjs` (upgrade of an existing database).
